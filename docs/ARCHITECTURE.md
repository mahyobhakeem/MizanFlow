# المعمارية التقنية والتصميم البرمجي — MizanFlow
**المشروع:** MizanFlow  
**الإصدار:** 1.0 (Phase 1 Specification)  
**النمط المعماري:** Standard Laravel Layered Architecture (MVC) معززة بطبقة الخدمات والعمليات المنفصلة (`Actions` & `Domain Services`).  

---

## 1. النظرة المعمارية العامة (Architecture Overview)

يعتمد MizanFlow على معمارية معيارية حديثة ومستقرة، ترتكز على إطار العمل **Laravel 13** مع **PHP 8.3+**، وتستفيد من أحدث قدرات محرك **MySQL 8.4 LTS**. تم تصميم المعمارية لتكون نظيفة، خالية من التعقيد المفرط (Over-engineering)، مع ضمان أقصى درجات الاتساق المالي والمخزني تحت ظروف العمل المتزامنة.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        User Interface (Blade + RTL)                    │
│             Bootstrap 5 RTL + JavaScript (Vite) + Keyboard POS         │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTTP Requests (CSRF Protected)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                       Presentation Layer (HTTP)                        │
│   • Middleware (Auth, Role Check, RTL Direction, Localization)         │
│   • Controllers (Thin: Request Dispatch, View Rendering, JSON Response)│
│   • Form Requests (Strict Type-Casting, Business Validation Rules)      │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Validated DTO / Request Data
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                     Domain & Business Logic Layer                      │
│   • Actions (Single Responsibility: CreateSale, PostPurchase, etc.)    │
│   • Services (Calculation: CalculateWACService, StockAuditService)     │
│   • Transactions & Locks (DB::transaction + lockForUpdate)             │
│   • Events & Listeners (StockMovementLogged, LowStockTriggered)        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Eloquent Queries & Transactions
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        Data Layer (Persistence)                        │
│   • Eloquent Models (Relationships, Mutators, Local Scopes)           │
│   • MySQL 8.4 Database (InnoDB, Foreign Keys, Strict Unique Indexes)   │
│   • Immutable Audit & Movement Logs (Stock Movements Ledger)           │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. طبقات التطبيق ومسؤولياتها (Layer Responsibilities)

### 2.1 طبقة العرض والتحكم (Controllers & Form Requests)
* **المتحكمات النحيفة (Thin Controllers):** تنحصر مسؤولية المتحكم في:
  1. استقبال طلب HTTP.
  2. استدعاء فئة التحقق `FormRequest`.
  3. تمرير البيانات المفحوصة إلى `Action` أو `Service`.
  4. إعادة التوجيه مع رسالة نجاح أو إرجاع قالب Blade المناسب.
  * *قاعدة صارمة:* لا توجد استعلامات مالية معقدة أو عمليات خصم مخزون مباشرة داخل المتحكمات.
* **فئات التحقق (Form Requests):** مسؤولة عن التحقق الصارم من المدخلات (الأنواع، الحدود الدنيا، وجود المعرفات في قواعد البيانات، والتحقق المخصص مثل التأكد من أن المستودع المصدر يختلف عن المستودع الهدف في عمليات التحويل).

### 2.2 طبقة منطق الأعمال والعمليات (Actions & Domain Services)
تُستدعى هذه الطبقة لتنفيذ العمليات التي تغير حالة النظام وتتطلب اتساقاً متعدد الجداول:
* **فئات الإجراء (Actions):** كل فئة مسؤولة عن مهمة تجارية محددة واحدة (`Single Responsibility Principle`)، مثل:
  * `CreateSaleInvoiceAction`: إنشاء فاتورة بيع، حجز/خصم المخزون، وتسجيل الدفعة النقدية.
  * `PostPurchaseInvoiceAction`: اعتماد فاتورة الشراء، زيادة رصيد المستودع، وتحديث متوسط التكلفة المرجح.
  * `ExecuteStockTransferAction`: نقل البضاعة من حالة "المصدر" إلى "في الطريق" ثم إلى "المستلم".
  * `ExecuteStockAdjustmentAction`: تسجيل العجز أو الفائض مع تسوية التكلفة.
* **فئات الخدمات (Services):** دوال حسابية وتدقيقية متخصصة:
  * `WeightedAverageCostService`: المسؤولة عن حساب المعادلة الرياضية لـ WAC بدقة عشرية عالية.
  * `DocumentNumberGeneratorService`: المسؤولة عن توليد أرقام تسلسلية فريدة وآمنة ضد التكرار لكل نوع مستند (`INV-2026-000001`, `PO-2026-000001`).

### 2.3 طبقة البيانات والاتساق (Data & Persistence Layer)
* **نماذج Eloquent:** تحوي العلاقات (`Relationships`)، وعوامل التصفية المتكررة (`Local Scopes`)، والمحولات (`Casts`) للتأكد من أن الأرقام العشرية والتكاليف تُعامل بالدقة المطلوبة.
* **سجل الحركات غير القابل للتعديل (`stock_movements`):** دفتر الأستاذ المخزني الذي يسجل كل حركة دخول أو خروج أو تحويل كحركة مستقلة لا تحذف أبداً.

## 3. استراتيجية التزامن ومنع البيع بالسالب (Concurrency & Locking Strategy)

في بيئات نقاط البيع والمستودعات المتعددة، قد يحاول أكثر من كاشير بيع الصنف نفسه من نفس المستودع في اللحظة ذاتها. لمنع نفاد المخزون والبيع بالسالب، يعتمد MizanFlow على:

### 3.1 القفل التشاؤمي (Pessimistic Locking)
* يتم تغليف عملية إصدار فاتورة البيع بالكامل داخل معاملة قاعدة بيانات (`DB::transaction`).
* قبل قراءة الرصيد وخصم الكمية، يتم حجز صف رصيد المنتج في المستودع المختار باستخدام `lockForUpdate()`:
  ```php
  DB::transaction(function () use ($warehouseId, $items, $saleData) {
      foreach ($items as $item) {
          // قفل السجل لحظياً لمنع القراءة المتزامنة الخاطئة
          $stock = ProductWarehouse::where('product_id', $item['product_id'])
              ->where('warehouse_id', $warehouseId)
              ->lockForUpdate()
              ->firstOrFail();

          if ($stock->quantity < $item['quantity']) {
              throw new InsufficientStockException(
                  "الكمية المتوفرة من المنتج [{$item['name']}] غير كافية لإتمام البيع."
              );
          }

          // خصم الكمية وتسجيل التكلفة التاريخية وحركة المخزون
          $stock->quantity -= $item['quantity'];
          $stock->save();

          // تسجيل في سجل الحركة stock_movements
      }
      // حفظ الفاتورة وبنودها
  });
  ```
* **لماذا القفل التشاؤمي وليس التفاؤلي؟**  
  في قطاع التجزئة والمستودعات، لا يمكن إخبار العميل الواقف أمام الكاشير بأن العملية فشلت بسبب "تعارض في النسخة"؛ القفل التشاؤمي يضمن معالجة الطلبات متسلسلة بدقة في أجزاء من الثانية ويمنع أي رصيد سالب نهائياً.

## 4. معمارية حساب التكلفة: المتوسط المرجح للتكلفة المتحرك (Moving WAC)

لضمان دقة هوامش الربح وتقييم المخزون، يُطبق النظام خوارزمية **المتوسط المرجح للتكلفة المتحرك لكل منتج في كل مستودع**:

### 4.1 المعادلة الرياضية المعتمدة
عند استلام كمية جديدة بسعر شراء محدد:
$$\text{WAC}_{\text{new}} = \frac{(\text{Qty}_{\text{current}} \times \text{WAC}_{\text{current}}) + (\text{Qty}_{\text{received}} \times \text{Cost}_{\text{unit}})}{\text{Qty}_{\text{current}} + \text{Qty}_{\text{received}}}$$

### 4.2 قواعد إدارة التكلفة
1. **عند الشراء:** يُعاد احتساب WAC في المستودع المستلم فور اعتماد فاتورة الشراء.
2. **عند البيع:** تخرج البضاعة بمتوسط التكلفة الحالي `WAC` للمستودع، ولا يتغير `WAC` المتبقي للوحدة الواحدة، ولكن يتم تجميد هذه التكلفة في جدول `sale_items.unit_cost` لحساب ربح الفاتورة لاحقاً بدقة تامة.
3. **عند التحويل بين المستودعات:**
   * تخرج البضاعة من المستودع المصدر بـ WAC الخاص بالمصدر.
   * عند استلامها في المستودع الهدف، تُعامل كدفعة واردة وتدخل في معادلة WAC للمستودع الهدف بالتكلفة التي خرجت بها من المصدر.
4. **في حالة نفاد المخزون (رصيد = 0):** إذا أصبح الرصيد صفراً، فإن أي كمية جديدة واردة تصبح تكلفتها هي الـ WAC الجديد مباشرة.

## 5. مبدأ عدم القابلية للتغيير في المستندات المعتمدة (Immutability of Posted Transactions)

حرصاً على سلامة النظام من التلاعب المالي أو اختفاء الحركات:
1. **الفواتير المعتمدة مقفلة نهائياً (Immutable):** بمجرد تحول حالة فاتورة المبيعات أو المشتريات إلى معتمدة (`Approved` / `Completed`)، يُعطل خيار التعديل أو الحذف المباشر نهائياً عبر واجهة المستخدم والـ API والسياسات البرمجية (`Policies`).
2. **آلية التصحيح المحاسبية والمخزنية:**
   * **تصحيح فاتورة بيع:** يتم حصرًا من خلال إصدار مستند **مردود مبيعات (Sales Return)** أو إشعار دائن (Credit Note) يعيد الكميات ويوثق استرجاع المبلغ أو تصحيح الرصيد.
   * **تصحيح فاتورة شراء:** يتم عبر إصدار **مردود مشتريات (Purchase Return)**.
   * **تصحيح فروقات الجرد:** يتم عبر **تسوية جردية رسمية (Stock Adjustment)** تتطلب سبباً موثقاً واعتماداً من المدير.
3. **التدقيق الدائم:** كل حركة أصلية وحركة تصحيحية تظهر في سجل كشف الحساب وكشف حركة الصنف دون شطب التاريخ القديم.

## 6. استراتيجية التدويل واللغات والـ RTL (Localization Architecture)

1. **العزل التام للنصوص:** لا توجد نصوص عربية أو إنجليزية مكتوبة بشكل مباشر (Hardcoded) في المتحكمات أو قوالب العرض؛ جميع العبارات تُستدعى عبر دوال الترجمة:
   ```blade
   {{ __('inventory.warehouse') }}
   {{ __('messages.sale_completed_successfully') }}
   ```
2. **دعم الـ RTL الأصيل:**
   * يتم استدعاء حزمة `bootstrap.rtl.min.css` وتحديد وسم الاتجاه في القالب الأساسي:
     ```html
     <html lang="{{ app()->getLocale() }}" dir="{{ app()->getLocale() == 'ar' ? 'rtl' : 'ltr' }}">
     ```
   * الخط المعتمد افتراضياً هو خط عربي واضح وعالي الدقة للشاشات التجارية (Cairo أو IBM Plex Sans Arabic).
3. **الجهوزية للغة الإنجليزية (English Readiness):**
   * هيكل مجلدات اللغات: `lang/ar/` و `lang/en/`.
   * تفعيل اللغة عبر جلسة المستخدم (`session('locale')`) ومتحكم سريع لتبديل اللغة، بحيث يمكن تفعيل الواجهة الإنجليزية في المستقبل فقط بإضافة ملفات `lang/en/` دون أي تغيير في البنية التحتية.

## 7. الأمان وإدارة الصلاحيات (Security & RBAC)

1. **التحكم بالوصول المبني على الأدوار (Role-Based Access Control):**
   * اعتماد نظام الصلاحيات المدمج في Laravel عبر `Gates` و `Policies`.
   * لكل نموذج رئيسي (`ProductPolicy`, `SalePolicy`, `PurchasePolicy`, `WarehousePolicy`) شروط دقيقة تحدد ما يمكن للـ `Cashier` والـ `Operations Manager` والـ `Administrator` فعله.
2. **حماية العمليات المالية الحساسة:**
   * التحقق من الـ CSRF في جميع نماذج الإرسال.
   * منع التمرير المفرط للمتغيرات عبر تفعيل الحماية في الـ Mass Assignment في نماذج Eloquent (`$fillable` الصارم).
   * تطهير المدخلات والاستعلامات المعلمة (Parameterized Queries) المضمنة في Eloquent ضد هجمات SQL Injection.
